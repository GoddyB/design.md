- (direction) User: spec what belongs in a strong DESIGN.md (tokens, sections, quality bar, omissions); extract from sources; do not elicit taste — that is bmad-ux next. Slug: perfect-design-md.
- (constraint) Do not spec the @google/design.md CLI, linter implementation, Tailwind export, or DTCG JSON pipeline (intake exclude list).
- (decision) YAML frontmatter is optional in the format spec; a strong DESIGN.md always includes it. Two-layer file is mandatory: tokens are normative values; markdown prose is application rationale and must not contradict tokens.
- (capability) CAP-1 Two-layer identity: a coding agent reconstructs visual identity from one DESIGN.md using exact tokens plus prose for when/why. Success: ---fenced YAML + ## body; tokens normative; Overview covers gaps.
- (capability) CAP-2 Token coverage: agent styles color, type, spacing, corners, and components without inventing values. Success: colors (incl. primary), typography (fontFamily+fontSize min), rounded, spacing, components — or omitted with reason. Fill colors used on text have contrasting textColor.
- (capability) CAP-3 Application rationale: agent applies the system in undefined cases and avoids brand-breaking moves. Success: body-sections.md order; Overview names personality, audience, emotion; Colors/Typography/Layout/Elevation/Shapes/Components carry usage rules; guardrails as Do's and Don'ts or inline.
- (capability) CAP-4 Composable references: component and variant tokens reuse primitives. Success: {path.to.token} resolve; non-component refs are primitives; components may ref composite typography; variants are sibling keys; primary action has default + hover/interactive variant.
- (capability) CAP-5 Intentional omission: consumer can tell a deliberate gap from an unfinished file. Success: absent token groups/sections listed in omitted; strong files include reason.
- (capability) CAP-6 Example-grade completeness: file matches official examples' density, not a parseable skeleton. Success: quality-bar.md checks all hold.
- (constraint) Present ## sections must appear in canonical order. Duplicate headings invalidate the file. Optional h1 is title-only, not a section. Unknown headings are preserved.
- (constraint) Color: any valid CSS color; hex #RRGGBB is the recommended default unless alpha or wide-gamut is required. Dimension units: px, em, rem. fontWeight is numeric. lineHeight may be Dimension or unitless multiplier (unitless preferred).
- (constraint) If colors exist, primary must exist (agents otherwise auto-generate). If colors exist, typography must exist (agents otherwise default fonts).
- (constraint) Component backgroundColor/textColor pairs must meet WCAG AA 4.5:1 for normal text. Colors are converted to sRGB for contrast checks; original format is preserved.
- (constraint) No elevation token group in the schema. Depth recipes live in Elevation & Depth prose (blur, opacity, border, glow) and may appear as rgba literals on glass components.
- (constraint) Token refs wrapped in {path.to.token}. Max reference depth 10, max nesting depth 20. Non-component refs must point at primitives; components may reference composite typography.
- (constraint) Unknown color/typography token names accepted if values type-check. Unknown component properties accepted with warning. Unknown top-level YAML keys that look like schema typos (colours vs colors) are not valid extensions. Token-like values under unknown keys suggest a dropped/misspelled group.
- (constraint) This spec does not choose palette, typeface, mood, or layout model. bmad-ux supplies taste against this contract.
- (decision) Do's and Don'ts is a canonical section but optional as a heading: all three official examples omit it and embed guardrails in other sections. CAP-3 still requires concrete do/don't rules somewhere.
- (decision) Recommended token names are non-normative guidance. Any descriptive scale-level or token name is valid. Official examples use Material-style roles and domain component names beyond the recommended list.
- (decision) Strong means example-grade application density, not merely schema-valid. Required for strong: surface (or equivalent canvas), on-surface (or equivalent body text), on-* (or textColor) for every hue used as a component fill, error if inputs exist. Full M3 inverse/fixed ladders are example pattern, not mandatory.
- (decision) Spec text says most systems have 9–15 typography levels; official examples have 6–8. Strong floor: at least one display or headline level, one body level, one label level — not a 9-level minimum.
- (decision) Companions: token-schema.md (YAML types, groups, refs, omitted, recommended names), body-sections.md (order, aliases, per-section load), quality-bar.md (example-derived completeness checks).
- (assumption) Official examples omit version, description, omitted, and ## Do's and Don'ts; a strong file may too if CAP-3 and CAP-5 are otherwise met.
- (assumption) Example READMEs establish DESIGN.md as the source artifact and Tailwind/DTCG as derived consumers — those derived files are out of scope, not quality criteria.
- (assumption) rounded.DEFAULT and named spacing keys (gutter, margin, glass-padding, container-max) are valid scale levels (schema: any descriptive string key).
- (question) Format has no first-class light/dark (or multi-theme) split; examples are each one theme. If the product needs both, bmad-ux must choose a convention (suffixes in one file vs two files) — not specified here.
- (note) Wrapper-only dropped: CLI install/Windows/ENOVERSIONS, lint/diff/export/spec command surfaces, programmatic API, lint JSON examples, example README file tables, generated-from header on docs/spec.md, empty Prose and Tokens stub heading.
- (decision) Color tokens are derived from palettes named in prose; mapping may use any consistent naming convention. Non-solid canvases (gradient, image) are specified in prose; colors values stay solid CSS.
- (decision) Component padding prefers Dimension or {ref}; official examples also use CSS shorthand (0 24px), transparent, and rgba glass fills — allowed literals, not a second schema.
